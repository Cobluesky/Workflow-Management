# 코드 리뷰 예시

## 1. 좋은 예시

### 예시 1: 인증 식별자 문제 지적
좋은 코멘트:
> 이 변경은 `authUserId` 대신 이메일을 영구 식별자로 사용하고 있습니다. 현재 구조에서는 이메일이 과도기 fallback일 뿐이라, 이메일 변경 시 로컬 사용자 매핑이 깨질 수 있습니다. `verify.user.id`를 기준으로 조회하거나, 최소한 `authUserId`를 우선 조회하도록 바꾸는 편이 안전합니다.

좋은 이유:
- 문제를 구체적으로 짚음
- 왜 위험한지 설명함
- 수정 방향이 있음

### 예시 2: 운영 배포 문제 지적
좋은 코멘트:
> 컨테이너 내부에서 `localhost:3306`을 사용하면 호스트 MariaDB가 아니라 컨테이너 자신을 가리킬 수 있습니다. 현재 운영 구조가 호스트 DB 기반이면 `host.docker.internal` 또는 명시적 네트워크 구성이 필요합니다. 이 상태로는 운영에서 `P1001` 연결 실패가 날 가능성이 큽니다.

좋은 이유:
- 재현 가능한 운영 리스크를 말함
- 프로젝트 맥락을 반영함

### 예시 3: 문서/코드 불일치 지적
좋은 코멘트:
> API 문서에는 `logout`이 Bearer 토큰 기반으로 적혀 있는데, 실제 구현은 Refresh Token 쿠키만 있으면 동작합니다. 운영팀과 프론트가 잘못 붙을 수 있어서, 문서나 구현 중 하나를 맞춰야 합니다.

좋은 이유:
- 문서와 구현의 불일치를 빠르게 드러냄
- 실제 협업 비용을 줄이는 지적임

## 2. 나쁜 예시

### 예시 1: 취향만 말하는 리뷰
나쁜 코멘트:
> 저는 이런 코드 스타일 별로예요.

왜 나쁜가:
- 근거가 없음
- 동작/위험과 무관함
- 수정 기준이 없음

### 예시 2: 막연한 부정
나쁜 코멘트:
> 이거 뭔가 위험해 보이네요.

왜 나쁜가:
- 무엇이 위험한지 알 수 없음
- 작성자가 다음 행동을 정할 수 없음

### 예시 3: 공격적인 표현
나쁜 코멘트:
> 이런 것도 테스트 안 하고 올렸나요?

왜 나쁜가:
- 사람을 겨냥함
- 협업 분위기를 해침
- 실제 문제 해결에 도움 안 됨

## 3. 더 나은 표현으로 바꾸기

나쁨:
> 이거 틀렸어요.

좋음:
> 현재 구현 기준으로는 이 분기에서 `refreshToken`이 없어도 `200`이 반환됩니다. 문서가 `401`을 기대하고 있으면 둘 중 하나를 맞춰야 합니다.

나쁨:
> 로직이 이상합니다.

좋음:
> `userByAuthUserId`와 `userByEmail`가 서로 다른 로컬 사용자를 가리킬 수 있는 분기라, 계정 충돌이 생길 수 있습니다. 이 경우는 명시적으로 `409`를 반환하는 편이 안전합니다.

나쁨:
> env 처리 다시 하세요.

좋음:
> `docker --env-file` 기준으로는 따옴표까지 값에 포함될 수 있습니다. `DATABASE_URL`에 따옴표가 들어가면 Prisma가 `mysql://` 프로토콜을 인식하지 못할 수 있어, 예시와 배포 스크립트를 같이 정리하는 편이 좋겠습니다.

## 4. 승인 코멘트 예시

좋은 승인:
> 핵심 인증 흐름은 테스트와 함께 잘 정리됐습니다. 특히 `authUserId` 우선 매핑과 이메일 fallback 분리가 명확해서, 현재 과도기 구조와도 잘 맞습니다. 다만 운영 DB 이관 전까지는 `workspace_auth` 준비 절차가 문서로 같이 따라가야 합니다.

좋은 이유:
- 잘한 점을 구체적으로 말함
- 남은 리스크도 같이 남김
- 승인과 후속 과제를 함께 정리함
