# 코드 리뷰 기본 규칙

## 1. 목적
- 코드 리뷰의 목표는 병합 자체가 아니라 품질, 안전성, 유지보수성을 높이는 것이다.
- 리뷰는 작성자를 평가하는 자리가 아니라 코드와 설계를 검증하는 과정이다.
- 리뷰어는 가능한 한 빠르게 위험을 식별하고, 해결 가능한 형태로 피드백을 남긴다.

## 2. 기본 원칙
- 먼저 동작과 위험을 본다.
- 스타일보다 동작, 보안, 데이터 무결성, 운영 리스크를 우선한다.
- 지적만 하지 말고 수정 방향까지 제시한다.
- 추측보다 근거를 남긴다.
- 프로젝트의 현재 아키텍처 방향을 기준으로 판단한다.

## 3. 리뷰 우선순위

### 3.1 가장 먼저 볼 것
- 인증/인가 우회 가능성
- 데이터 손실 가능성
- 잘못된 DB 마이그레이션
- 토큰/쿠키/시크릿 노출
- 운영 배포 실패 가능성
- API 계약 변경에 따른 하위 호환성 문제

### 3.2 그 다음 볼 것
- 아키텍처 일관성
- 테스트 누락
- 예외 처리 누락
- 메시지와 에러 코드의 일관성
- 코드 복잡도 증가

### 3.3 마지막에 볼 것
- 사소한 네이밍
- 포맷팅
- 취향 차이 수준의 스타일

## 4. 이 저장소에서 특히 중요하게 볼 것

### 4.1 인증 경계
- 인증의 진실 원본은 `auth-server` 여야 한다.
- 앱 서비스는 비밀번호 검증 책임을 다시 가져오면 안 된다.
- `app` 계층은 `auth-server` 검증 결과를 기준으로 동작해야 한다.

### 4.2 사용자 식별자
- 장기 기준 식별자는 이메일이 아니라 `authUserId`다.
- 이메일 기반 매핑은 과도기 fallback으로만 허용한다.
- 새 코드가 이메일을 영구 식별자로 전제하면 리뷰에서 막아야 한다.

### 4.3 클라이언트 입력 신뢰
- 클라이언트가 보낸 `userId`를 그대로 신뢰하면 안 된다.
- 보호 API는 인증된 사용자 기준으로 서버가 사용자 식별을 결정해야 한다.

### 4.4 배포/운영
- Docker 컨테이너에서 호스트 DB를 쓸 때 `localhost`는 위험하다.
- 운영 env는 `--env-file` 기준으로 해석된다는 점을 고려해야 한다.
- env 값에 불필요한 따옴표를 넣으면 런타임에서 깨질 수 있다.

### 4.5 보안
- 시크릿, OAuth secret, JWT secret은 코드/문서/예시에 평문으로 남기지 않는다.
- Access Token을 query string에 실어 나르는 현재 구조는 과도기임을 전제로 본다.
- Refresh Token은 반드시 `HttpOnly` 쿠키 기준으로 다뤄야 한다.

## 5. 리뷰 코멘트 작성 규칙
- 문제를 먼저 말하고, 왜 문제인지 짧게 설명한다.
- 가능하면 재현 조건이나 깨지는 시나리오를 붙인다.
- 수정 방향이 있으면 제안한다.
- 단정적인 표현보다 검증 가능한 표현을 쓴다.

좋은 형태:
- "이 변경은 `authUserId`를 우회하고 이메일을 영구 키로 사용해서, 이메일 변경 시 사용자 매핑이 깨질 수 있습니다."
- "여기서는 컨테이너 내부 `localhost`가 호스트 MariaDB를 가리키지 않아서 운영에서 연결 실패가 날 수 있습니다."

피해야 할 형태:
- "이상함"
- "그냥 별로"
- "제 취향에는 안 맞음"

## 6. 승인 기준
- 치명적인 보안/데이터 무결성 이슈가 없을 것
- 주요 API 계약 변화가 문서와 테스트에 반영될 것
- 최소한의 회귀 테스트 또는 수동 검증 근거가 있을 것
- 현재 아키텍처 방향과 충돌하지 않을 것

## 7. 보류 또는 변경 요청 기준
- 인증 책임이 잘못된 서비스로 새어 나갈 때
- DB 스키마 변경이 마이그레이션 계획 없이 들어올 때
- 운영 env/배포 가정을 코드에 하드코딩할 때
- 테스트 없이 핵심 인증 흐름을 바꿀 때
- 문서/API 계약과 실제 구현이 어긋날 때
